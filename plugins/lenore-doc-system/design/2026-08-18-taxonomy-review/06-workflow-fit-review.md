# 3. Stress points

**S1 — Proposals are the single largest unhomed class, and the user generates them on command.** Two this session; `docs/proposals/` holds 13, with a working lifecycle (`Status: Proposed / Accepted / Deferred / Superseded`, `-IMPLEMENTED` suffix, INDEX rows). Both new ones are **DEFERRED** — that's the state the taxonomy can't express. `spec` covers *adopted* contracts (openspec); nothing covers *designed but parked*. And I checked: design docs 01–04 never analyze proposals as a type. 01's "What I would explicitly not add" rejects `plans/` on the grounds that "designed plans belong in OpenSpec changes" — which is exactly the assumption this session breaks, twice, on user instruction, with a two-year unfreeze horizon. This is not a bend the user should make; deleting the deferred-proposal state loses real work.

**S2 — Premises have no tier, and `model` is the wrong shape for them.** This is the strongest evidence in the log, and it isn't mine — it's the user's own subagent, in this session, running exactly this analysis against the incumbent system and arriving at a fourth doc. Its §1.1 finding is a fact rather than an argument: the freshest statement of product intent in the repo (`algorithms.md` §3.0, written at the user's direction, opening *"read it before changing a threshold"*) sits **underneath a "Superseded 2026-07-24 — do not read as current" banner**, in a section-read-only file, reachable only by an agent implementing QualityGate — while its actual consumers are the drizzle weighting, the revisit policy, and the operator UI. Its scope test is clean and worth stealing verbatim: **"Would this still be true if we rewrote the entire pipeline in another language tomorrow?"** The proposal's `model` is hub-and-chapters organized **by subject** — structurally the same shape that buried §3.0. A cross-cutting premise filed under one chapter is invisible to the other three consumers. The proposal also enumerates and kills the obvious cheap fixes: fold into the working rules (destroys their domain-free transferability, and re-runs a context-exhaustion failure `lessons.md` already records), or fold into the failure registry (every field presupposes a defect — *"the mosaic should be better than any single input frame"* has no Trigger and no Detector).

**S3 — Pull-only retrieval vs. the user's explicit push requirement.** Same turn: *"maybe we should have the doc be read by every agent. Like a line in Claude.md that directs them to read the file and a file that an agent can refer to anytime to see if their design is meeting the standard and requirements of the project."* That is a **mandatory-read + self-check** mechanism. The proposed system is demand-driven promotion plus a browse contract — pull. Paired with *"where did you keep that report and how will a new session be able to find it in the future?"*, retrieval is a stated user requirement, not a nice-to-have.

**S4 — Multi-file research bundles.** Already raised as open challenge #2 in `05-synthesis`; this session confirms it twice (the 3-file advice bundle, the 4-CSV evidence dir) and adds a wrinkle the synthesis doesn't have: the user asks for **live progress files** so a long-running agent's work isn't lost. Immutable dated notes forbid that.

**S5 — Images and their sources.** Challenge #1 in `05-synthesis` is right but understated. The problem isn't "images beside chapters" — that's allowed. It's that the *sources* (`.d2`, `.excalidraw`, `.excalidraw.py`) are rejected by the prose-only hook, and the round-trip in P3 (garbled excalidraw → user screenshots it → regenerate with d2 → also render with tldraw) proves diagrams here are iterated, not deposited. Same hook blocks the CSV evidence dir. Both are **day-one adoption blockers**, checkable, not matters of taste.

**S6 — Candidate systems.** §4 below.

**S7 — The one thing the system removes that the user is actively using.** `docs/INDEX.md` is a hand-maintained dashboard carrying **path · tier · status · one-line purpose**, and it is where a deferred proposal announces itself. The proposal bans hand-maintained indexes in favour of a computed one. A computed index can carry a path and a first line; it cannot carry *"Planned — DEFERRED (2026-08-18) … Unfreeze after real-hardware stitching."* If deferred designs get a home (S1), they need a status surface too.

**Bends that are reasonable discipline** (user should bend, no value lost): retract-in-place inside a 51KB README → immutable run entries with supersede pointers (the *content* of the retractions is excellent — it's the mutation that's wrong); undated ad-hoc experiment dirs (`focus-defocus-gt`, `focus-defocus-sim`); probe outputs written to `/tmp` and then relocated after a complaint (the run-id reservation is strictly better than what happened); `pending.md` as catch-all (they self-corrected once already, in this session).

# 4. The simple-pipeline question

**What's actually in it.** `Package.swift`, `Sources/CanvasTrackerHarness/`, `Tests/`, ~20 prose docs (`dream-pipeline-founding-plan.md`, `pc-pipeline-plan.md`, `virtual-camera-iosurface-architecture.md`, `resampling-impl-plan.md`, two dated `review-*.md`, `HANDOFF.md` + `HANDOFF-pc-integration.md`, several `*-findings.md` and `*-risk.md`), ~30 JSON scenario files under `paths/` + `paths-next/`, `results/`, and a `README.md` + `notebook.md` pair. No date in the dir name.

**It already contains the answer, twice.** Its README is a genuine **document map** (per-file "what it is", a Tools section, a Scenario suite section, "Status at a glance") that routes outward to `openspec/changes/*`, `docs/pending.md`, and a memory file. Its `notebook.md` opens with a **Synthesis** narrative and carries a **"Dead ends & ruled-out"** register — *"what we tried, set aside, and why — read this before re-opening any of those threads."* That is exactly the README/notebook split the Lenore convention wants, invented independently, and better on one axis.

**And the lifecycle already exists in the tree.** `experiments/_records/simple-pipeline.md` is a retrospective arc summary — Change A / Change B / finding D10, with commit provenance — and it names **`docs/reference/tracking-statechart.md` as the SSOT**, i.e. the doc shared with production, plus a verified note that the PC deltas *are not yet synced* into it. And `docs/reference/retired-pipelines.md` is the retire arm: a living registry pointing at the `pre-pipeline-removal` git tag. So the real lifecycle the user runs is:

> candidate keeps its own docs inside → **one canon-side pointer naming the shared SSOT** → on adoption, docs promote to model chapters (+ a PROMOTIONS line) → on rejection, canon keeps a pointer to git history and the tree gets deleted.

**Evaluating "keep it in experiments/, promote docs to model on adoption."** The promote arm is right, and the containment is right — a candidate's architecture docs must not sit in `docs/model/` while it's a candidate, or the spine acquires a second, competing "how it works now." But as written the option is a **category mismatch** on two counts. (a) The Lenore experiment convention is `YYYY-MM-DD-<name>/` + README-as-current-truth + `notebook/runNNN.md` immutable run entries + gitignored data store. A buildable Swift package with 20 design docs and a scenario suite has no runs to number and no date that means anything. Forcing it in either breaks the convention or breaks the candidate. (b) The option specifies only the promote arm — no pointer, no retire, no park. The pointer is the load-bearing one: without it, a candidate's SSOT claim on a production doc (`tracking-statechart.md`) is invisible from the spine, which is precisely the drift `_records/simple-pipeline.md` had to be written to catch.

**Proposal — a `kind` field, not a new directory.** Keep candidates under `experiments/`. Add one front-matter field to the experiment README: `kind: candidate-system` (default `question`). It buys three exemptions and imposes three requirements:

- *Exempt from* the dated-dir name, the `notebook/runNNN` structure, and the gitignored-data-store requirement (a candidate has a `results/`, not runs).
- *Requires* (i) a **document map** README section — already how `simple-pipeline` works, so it costs nothing; (ii) an **`ssot:` field** listing production docs the candidate claims or shares, which is what the spine points back at and what a lint can check for drift; (iii) a **verdict arm on conclusion** — `adopted` (docs copied to `docs/model/` chapters + PROMOTIONS line), `retired` (a one-line entry in the playbook's retired registry naming the git tag), or `parked` (README status flip only).

This adds one field and one registry line, no new top-level dir, and it makes both existing arms in this repo legal.

# 5. Verdict + top changes

**Verdict: strong fit on the half of the flow the system was designed for; a real gap on the half this user actually spends time in.** The spine is right for what this session produced as durable truth — E4 is a textbook caveat and the user policed its routing themselves; `handoff.md` is a textbook branch task file; the browse contract the user already runs (INDEX + Canon only, evidence is historical) is the same discipline the spine formalizes. But this session's *characteristic* output is not a settled belief. It is a **designed-but-deferred proposal**, a **commissioned multi-author advice bundle**, a **cross-cutting premise about the instrument and the operator**, and a **published artifact** — and the taxonomy has no slot for any of the four. Adopted as written, roughly half of what these 54MB produced would be filed as "dated note" (which is where the ten-second rule sends anything it can't classify) and lose its status, its structure, or its authors.

**Ranked design changes:**

1. **Add a status-carrying, revisable design tier.** One dir, e.g. `docs/designs/YYYY-MM-DD-topic.md`, front-matter `status: proposed | accepted | deferred | superseded | implemented`. Revisable by rule (it's a plan, not a record), and the escape valve for shelved architecture. On `accepted` it becomes a spec (openspec) and the design freezes; on `implemented` its conclusions land in `model`. This one change homes items 6, 7, 8 in §2 and the two 50–60KB alt-pipeline docs. Rank 1 because it's the highest-volume gap and the user issues "write a proposal" as a direct command.
2. **Add a premises class + a push mechanism.** Either a fourth spine file (`premises`) or a designated mandatory-read `model` chapter, gated by the rewrite-in-another-language test, entries numbered and ID-cited (`per P7`) with a `provenance:` citation into evidence and a `consumers:` list. Pair it with the CLAUDE.md line the user asked for and a Part-II self-check section ("does my design meet the bar"). Their own agent did the four-option analysis and killed A, B, and C on evidence — you can adopt that verdict rather than re-derive it. Rank 2: it's the knowledge class the user called *"invaluable when making decisions and designing experiments."*
3. **Fix the `docs/` extension whitelist and allow dated bundles.** Two mechanical changes with one root cause. (a) Permit diagram sources beside their renders (`.d2`, `.excalidraw`, `.excalidraw.py`, and generator `.py`) — otherwise `docs/v3-arch/` is illegal and diagrams become un-regenerable. (b) Permit `notes/YYYY-MM-DD-topic/` as a **directory** with an index file, member files immutable, data files allowed (or symlinked to the store, with the symlink legal). This homes the advice bundle, the brief, and the CSV evidence dir. Rank 3 because these are hard adoption blockers, not preferences.
4. **Name the candidate-system kind** (§4): `kind: candidate-system` + `ssot:` + the three-arm verdict (adopted / retired / parked). One field, no new dir.
5. **Record published artifacts.** An `artifact:` URL field on note / experiment README / design front-matter, and a lint that says "an `.html` in the tree with no recorded URL." Today the only record that `a73f116c-…` exists is this jsonl.
6. **Preserve a status surface.** If deferred designs and candidate verdicts exist, the computed index must carry `status` (from front-matter) — or keep a thin hand-maintained status table. Banning hand-maintained indexes wholesale deletes the one thing this user's `INDEX.md` does that grep can't.

**Adopt wholesale from the user — these are better than what's proposed:**

- **The `Validity:` ladder on caveat entries.** E4 reads *Confirmed-reproduced* → *Operator-reported mechanism (and the one to work from)* → *Retracted, with the reason the earlier reading was wrong*, in that fixed order, headed *"Read the three lines in order."* Given this session's three reversals in 28 hours, a caveat shape without an epistemic-status ladder will produce entries that quietly assert retracted mechanisms. Make it a required field.
- **The "Dead ends & ruled-out" register** as a mandatory README section for any experiment or candidate — *"read this before re-opening any of those threads."* Costs no directory and is the single highest-leverage anti-rework device in the tree.
- **The retrospective arc record** (`experiments/_records/<name>.md`) — a from-outside summary of a multi-month line of work with commit provenance and its SSOT named. This is what makes a shelved candidate legible to a future session.
- **The user's own acceptance question** — *"where did you keep that report and how will a new session be able to find it in the future?"* — as a required closing check on any commissioned report or artifact.

**Where the user should bend (and it's cheap):** immutable run entries instead of retract-in-place inside a 51KB README; dated experiment dir names; reserving a run id before writing outputs instead of `/tmp`-then-relocate; routing hazards to the caveat registry rather than `pending.md` (already self-corrected once, unprompted, in this session — which is the best single signal that the routing rule matches how they actually think).
